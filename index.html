SentinelVision — Technical Report

The full system as designed: a privacy-first browser agent that perceives the screen locally, sanitizes sensitive content before any network call, and lets a cloud model reason only over the safe view.

Scope note: this document describes the complete target architecture. Each component is marked live (running today) or planned (designed, not yet implemented).

1. End-to-end architecture

Three trust zones. Nothing crosses the middle boundary except the sanitized image.

Capture through redaction: live (regex/heuristic detectors). Trained face/OCR models and the cloud round trip: planned.

2. Request lifecycle, step by step

1
User starts SentinelVision
One click, on the active tab only (activeTab permission)
2
Visible tab captured locally
Raw buffer held only in temporary memory, never written to disk
3
Local detection runs
UI elements, faces, text regions, and PII patterns identified with confidence scores
4
Privacy policy applies redaction
High confidence → placeholder; low confidence → expanded mask; failure → block
5
Validation gate checks the sanitized buffer
Confirms no raw reference, no leftover OCR text, all boxes covered
Only the sanitized image is allowed past this point
6
Cloud VLM reasons over the safe view
Returns one structured action as strict JSON
7
Local validator checks the action
Type on allowlist, coordinates inside viewport, target is a real safe element
8
Action executes, or user confirms first
Submit, pay, delete, upload, consent — always require explicit approval

5. Privacy decision policy

SignalResponse
High confidence PIITargeted redaction / explicit placeholder
Medium confidence PIIExpand the mask to safely cover the region
Low confidence PIILarger mask, ask the user, or block
Detector / OCR / redaction failureBlock transmission — fail closed
Unsupported content typeBlock or require explicit confirmation

6. Threat model

ThreatMitigation
Raw screenshot uploadPrivacy gate blocks any raw buffer from the network payload
OCR text leakageRaw OCR output stays local, never logged or sent
Missed PIIConservative thresholds, expanded masks, benchmark testing
Cloud action hallucinationStrict JSON schema, local allowlist, DOM verification
Prompt injection from the pagePage content treated as untrusted data, never as instructions
Sensitive audit logsMetadata only — no raw screenshots or PII ever stored
Cloud outage / rate limitTested fallback and a prerecorded demo backup

7. Action schema and validation

{
  "action": "click",
  "target": {"x": 742, "y": 516},
  "confidence": 0.93,
  "reason": "Visible next-step button"
}

Allowed: click, scroll, focus, highlight, open_dropdown, type_with_user_confirmation. Submit, pay, delete, upload, send, and consent always require explicit user approval before execution.

8. Evaluation framework

CriterionWeightHow it's measured
Visual context accuracy25%Correct page-state understanding on labelled screenshots
PII recall / precision20%Labelled benchmark; precision, recall, F1
Redaction precision20%Coverage, leakage rate, over-redaction rate
Client resource use20%CPU, memory, model size, execution provider
End-to-end latency15%Capture-to-action timing over repeated trials
Precision = TP / (TP + FP)   Recall = TP / (TP + FN)   F1 = 2·P·R / (P + R)

Scoring weight given to each criterion:

25%Visual context
20%PII recall/precision
20%Redaction precision
20%Resource use
15%Latency

Weights as defined in the evaluation framework — not a scored result.
